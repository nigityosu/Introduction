# 仕様レビューと技術スタック案

## 1. 結論

現在の仕様は、学習体験の方向性は明確です。一方で、画面構成・級の定義・試験の合格条件・対応する学習種類がまだ揺れているため、そのまま実装を始めると後から大きな作り直しが発生します。

まずは次の方針に固定することを推奨します。

- 学習段階は「初級」「中級」「上級」「卒業試験」の4段階とする
- 初級と中級はパズル、中級の後半から実際の言語要素を扱い、上級はコードエディタを使う
- 合格条件は各試験について「問題数」「合格率」「制限時間」「ヒントの扱い」を明記する
- 最初の対応対象は、ブラウザだけで完結し、成果を確認しやすい HTML/CSS/JavaScript に絞る
- アカウント、学習履歴、試験結果を保存するため、フロントエンドだけでなく認証・データベースを用意する

## 2. 矛盾点と変更が必要な箇所

### 2.1 ページ一覧とハンバーガーメニューが一致していない

ページ構成には「お問い合わせページ」がありますが、メニューの項目はホーム、学習履歴、説明ページの3種類と書かれています。お問い合わせページへ到達する導線がありません。

**変更案**

- メニューに「お問い合わせ」を追加する
- または、お問い合わせを説明ページ内のフォームとして扱い、独立ページから削除する
- 学習履歴はページとして扱うのか、ホーム内のセクションへ移動するのかを決める

推奨は、ホーム、学習一覧、学習履歴、説明、お問い合わせを独立したルートとして定義することです。

### 2.2 「上級」と「卒業試験」の関係が曖昧

「初級・中級・上級の三つ」と説明した後に、上級を卒業試験とする記述があります。また、別の箇所では上級と卒業試験が別の段階として説明されています。

**変更案**

学習状態を次の4段階に統一します。

1. 初級: 構造をパズルで組み立てる
2. 中級: 言語の要素を使うパズルで組み立てる
3. 上級: 雛形と補助機能を使ってコードを書く
4. 卒業試験: 補助機能を制限し、仕様に沿った成果物を作る

これにより、「上級の練習」と「卒業試験」を別の画面・別の合格条件として実装できます。

### 2.3 試験の問題数が一致していない

中級試験は「10個の要望から8個以上」と書かれていますが、卒業試験は「20問を8割正解」と書かれています。試験方式が異なること自体は問題ありませんが、試験名と条件を明示的に分ける必要があります。

**変更案**

- 中級試験: 10課題中8課題以上を達成
- 卒業試験: 20問中16問以上を正解、または成果物の評価を別に行う

「一致率」という表現は、何を比較するのかが不明確です。パズルの正解判定、コードのテスト、画面の見た目の比較のどれなのかを決め、「正解数」「自動テスト通過数」など実装可能な表現に変更します。

### 2.4 初級試験と中級試験の合格条件が不足している

初級試験には「最初のものを助けなしで作成」とありますが、「最初のもの」が何か、問題数、制限時間、再挑戦条件が未定義です。中級には「指南あり一回」とありますが、指南がヒント1回を意味するのか、チュートリアルを1回受けることを意味するのか不明です。

**決める項目**

- 試験の問題数
- 制限時間
- 合格率または必要な正解数
- ヒントを使った場合の減点の有無
- 再受験までの待ち時間の有無
- 途中保存の可否
- 合格後に解放されるコンテンツ

### 2.5 対応する学習種類と「言語」の単位が混在している

「サイト作成」「ゲーム制作」「ロボットソフト」は分野ですが、HTML/CSS/JavaScript、C#、Unity、C は言語・ツール・実行環境が混在しています。「各種類の初級＋言語ずつの中級」という表現では、学習経路が作れません。

**変更案**

次の3階層に分けます。

- 分野: Web制作、ゲーム制作、ロボット
- コース: Web基礎、Unity 2D、組み込み C など
- 技術: HTML、CSS、JavaScript、C#、Unity など

MVP では「Web制作 > Web基礎 > HTML/CSS/JavaScript」だけを対象にします。Unity や C は実行環境・教材・採点方法が大きく異なるため、Web基礎の完成後に別コースとして設計します。

### 2.6 上級・卒業試験の自動採点方法が未定義

コードを実行して採点する場合、ユーザーが入力したコードをサーバー上で直接実行するのは危険です。特に Python、C#、C などは、無制限実行・ファイルアクセス・ネットワークアクセスを防ぐ隔離環境が必要です。

**変更案**

- MVP の HTML/CSS/JavaScript は、ブラウザ内の iframe とテスト用スクリプトで採点する
- JavaScript の実行には iframe の sandbox 属性、実行時間制限、通信制限を設ける
- サーバー上でコードを実行する機能は、サンドボックスまたは専用の実行基盤を導入してから追加する
- 見た目だけでなく、DOM、イベント、出力値など検証可能な条件を課題ごとに定義する

### 2.7 アカウント要件が不足している

メールアドレス、パスワード、ニックネームの記載はありますが、メール確認、パスワード再設定、退会、個人情報の扱いが未定義です。

**変更案**

最低限、次を仕様に追加します。

- メールアドレスの重複確認
- パスワードのハッシュ化。平文保存は禁止
- パスワード再設定
- メール確認を必須にするかどうか
- 退会時の学習データ削除方針
- お問い合わせ内容の保存期間
- 未成年者を想定した個人情報・保護者向け案内

開発初期は仮ログインや匿名ユーザーで画面を作り、認証を後から差し込める構成にすると進めやすくなります。

### 2.8 「最後の学習履歴」が曖昧

メニューから「最後の学習履歴のところまで飛べる」とありますが、最後に学習したコースへ移動するのか、履歴一覧へ移動するのかが不明です。

**変更案**

メニューには次の2つを分けて用意します。

- 学習履歴: 過去のコース・課題・試験結果を見る
- 続きから学ぶ: 最後に未完了だった課題へ移動する

### 2.9 完了メッセージの文言を修正する必要がある

「おめでとう中途リアル終了だよ」は誤記または意図が読み取れないため、画面に表示する文言を確定してください。例えば「おめでとうございます。入門コースを修了しました。これからは実際の制作に挑戦してみましょう。」のように、対象者に伝わる表現にします。

また、「バカでかい文字」はアクセシビリティやスマートフォン表示を損なう可能性があります。目立たせる場合も、見出しサイズを CSS のレスポンシブな範囲で管理し、読み上げやキーボード操作を妨げないようにします。

## 3. 推奨する確定仕様の骨子

### 3.1 ルート

- `/`: ホーム
- `/about`: サイトの説明
- `/courses`: コース一覧
- `/courses/web-basics`: Web基礎の段階一覧
- `/lessons/:lessonId`: 通常の学習
- `/exams/:examId`: 試験
- `/history`: 学習履歴
- `/contact`: お問い合わせ
- `/settings`: アカウント設定

### 3.2 学習状態

課題ごとに `未開始`, `学習中`, `合格`, `不合格`, `解放済み` を持たせます。次の段階は、前の段階の必須課題と試験に合格した場合だけ解放します。

### 3.3 最初のコース

MVP は Web基礎コースに限定します。

- 初級: HTML 要素、CSS の配置、簡単な動きの構造をパズルで組む
- 中級: セレクター、イベント、条件分岐などを部品として組む
- 上級: 用意された HTML/CSS/JavaScript の雛形を編集する
- 卒業試験: 課題仕様に沿うページを作り、自動テストを通過する

## 4. 技術スタック案

### 4.1 フロントエンド

- React 19: 既存の採用方針を継続
- Vite: 開発サーバーと本番ビルド
- React Router: ページと学習状態に応じたルーティング
- CSS Modules または通常の CSS: まずは依存を増やさず、コンポーネント単位で管理
- Monaco Editor: 上級・卒業試験のコードエディタ。導入時はバンドルサイズを確認する
- dnd-kit: パズル部品のドラッグ＆ドロップ。キーボード操作にも対応しやすい
- Zod: 課題データ、試験設定、フォーム入力の検証

React と Vite は既に [package.json](package.json) に導入済みです。現時点の `App.jsx` は未実装なので、最初はモックデータで画面遷移と学習状態を作るのが適切です。

### 4.2 バックエンド・認証・データベース

費用を抑えて個人開発を始めるなら、Supabase を第一候補にします。

- Supabase Auth: メールアドレス、パスワード、パスワード再設定
- PostgreSQL: ユーザー、コース、課題、進捗、試験結果
- Row Level Security: 自分の学習履歴だけを読めるようにする
- Supabase Storage: 必要になった場合の提出ファイル保存

代替案は Firebase Authentication + Firestore です。ただし、試験結果や課題の関係を集計する処理は PostgreSQL の方が扱いやすいため、このサイトでは Supabase を推奨します。

### 4.3 データ構造の最小案

- `profiles`: ユーザーID、ニックネーム、作成日時
- `courses`: 分野、コース名、説明、公開状態
- `lessons`: コース、段階、教材、順序
- `exams`: 試験名、問題数、合格条件、制限時間
- `questions`: 問題文、問題種別、採点設定
- `progress`: ユーザー、課題、状態、最終学習日時
- `exam_attempts`: ユーザー、試験、得点、合否、受験日時
- `contact_messages`: お問い合わせ内容、状態、作成日時

課題データと採点条件は、コードに直接埋め込まず JSON またはデータベースで管理すると、問題追加と難易度調整が容易になります。

### 4.4 テスト・品質管理

- Vitest: 採点ロジック、進捗解放条件、フォーム検証
- React Testing Library: 学習画面、試験画面、メニューの操作
- Playwright: ログインから学習、試験合格、履歴表示までの E2E テスト
- ESLint または既存の oxlint: 静的解析。現在は `oxlint` が設定済み
- GitHub Actions: push 時の lint、build、test

特に採点ロジックは UI から分離し、入力と期待結果を用意した単体テストを先に作ります。

### 4.5 公開先と費用

初期構成は次の組み合わせが現実的です。

- フロントエンド: Vercel または Cloudflare Pages
- 認証・DB: Supabase の無料枠
- ソースコード管理と CI: GitHub Actions の無料枠
- 独自ドメイン: 初期は使わず、必要になってから取得

無料枠は利用量、保存容量、休止条件が変わる可能性があるため、公開前に各サービスの最新条件を確認します。利用者が増えた場合は、認証、データベース、コード実行環境の費用が別々に発生します。

## 5. 実装順序

1. HTML/CSS/JavaScript のコース定義と画面遷移を確定する
2. モックデータでホーム、コース、学習、試験、履歴を実装する
3. 初級パズルとローカルの正解判定を実装する
4. 中級の言語部品と試験の合格判定を実装する
5. ログインなしの進捗保存を追加する
6. Supabase Auth と PostgreSQL に置き換える
7. 上級のエディタと HTML/CSS/JavaScript の安全な採点を追加する
8. Playwright で主要な学習経路を検証する
9. お問い合わせ、パスワード再設定、退会などの運用機能を追加する
10. その後に Unity、C#、C など別のコースを設計する

## 6. 実装前に決める質問

- 最初の公開時点で対象にするのは Web基礎だけか
- 1つの課題の標準学習時間は何分か
- ヒントを使うと得点が下がるのか
- 合格後に次の課題を即時解放するのか
- 問題のランダム生成は、同じ難易度を保てる設計か
- 卒業試験は自動採点だけで合格にするのか、提出物の確認も行うのか
- 対象年齢と、未成年者のアカウント作成方針は何か
- お問い合わせへの返信を誰が、どの方法で行うのか
- 学習履歴や提出コードを何年間保存するのか

この質問への回答を仕様書に追記してから、画面の詳細デザインとデータベース設計に進むのが安全です。
